# Component hygiene

Rules for every page and component PR in `web/`. They are narrow on purpose: a reviewer can check each one by reading the diff or running one grep. `CLAUDE.md` §4 holds the frontend rules these build on (subscriptions, breakpoints, screenshot loop).

## Layout

| Path | Holds |
|---|---|
| `web/src/routes/` | TanStack Router route files (file-based): thin, see Rule 0 |
| `web/src/routeTree.gen.ts` | generated by the router's Vite plugin on `dev` and `build`; committed, never edited by hand, excluded from Biome |
| `web/src/auth/` | the auth store, role helper, route guards and the `next` check |
| `web/src/pages/<page>/` | one folder per screen: `<Name>Page.tsx`, its `<Name>Page.module.css`, page hooks (`use*.ts`) |
| `web/src/components/<Name>/` | shared pieces used by two or more pages: `<Name>.tsx` + `<Name>.module.css` |
| `web/src/shell/` | the app shell around every non-splash page (S14.1): bar, account area, banner, announcer, the splash rule; each component with its own `.module.css` |
| `web/src/styles/` | the only global CSS: `tokens.css`, `media.css`, `base.css`, plus `fonts.css` (the `@font-face` rules) |
| `web/src/lib/` | hooks and helpers with no markup (the old `lib/legacy/` reference copies were removed on 2026-11-17 by the user's ruling) |

Styling is CSS Modules plus tokens. No Tailwind, no CSS-in-JS, no inline `style` for static values (a `style` that passes a runtime value into a custom property is fine).

## Rule 0: thin route files

A file in `web/src/routes/` names the route and renders a page component from `web/src/pages/`. It may wire `validateSearch`, `beforeLoad` and the route's hooks (`Route.useSearch()`), but the validator, guard and page logic live elsewhere (`pages/<page>/`, `auth/`) as plain functions.

```tsx
// routes/standby.tsx
export const Route = createFileRoute('/standby')({
    validateSearch: parseStandbySearch,
    component: StandbyRoute,
});
function StandbyRoute() {
    const { module } = Route.useSearch();
    return <StandbyPage module={module} />;
}
```

In-app navigation uses the router's typed `Link` (`to`, `params`, `search` checked by `tsc`), never a string `href` on a plain `<a>`, so a typo or a missing param fails the typecheck and a click does not reload the page.

Search params are plain text (A169, `web/src/lib/searchParams.ts`): a validator receives strings (arrays for a repeated key), converts them itself, accepts its own output again (the router re-validates), and returns every key it owns, `undefined` when rejected.

## Rule 1: thin page files

A page file composes; it does not implement. It reads its hooks, picks its data and renders components. Business rules, derived data and effects live in hooks or components, so the same feature can appear in a second page or a dialog without surgery.

```tsx
// pages/standby/StandbyPage.tsx
export function StandbyPage({ module }: { module?: string }) {
    const moduleName = useRequestedModule(module);
    useDocumentTitle(moduleName ? `${moduleName} — Standby — IPC Battlegrounds` : 'Standby — IPC Battlegrounds');
    return <SplashLayout /* image, labels, title, lede */>{moduleName && <p className={styles.modulePill}>…</p>}</SplashLayout>;
}
```

## Rule 2: viewport-agnostic components

No component asks for the viewport (`useIsMobile`, `matchMedia` in render). One responsive page per screen (A13): the CSS adapts through the shared breakpoints or container queries; components take size or variant props when a parent needs a different presentation.

## Rule 3: responsive CSS adjusts, it does not hide real content

Media and container queries change sizing, spacing, columns and order of reading flow that stays in the DOM. They do not drop real content (text, controls, data) on one width. Decorative content, marked `aria-hidden` (a HUD line, a coordinate), may be hidden at small widths; so may a duplicate of a name that stays available another way (the brand word, while the link keeps its `aria-label`). If a phone needs a different arrangement of the same content, use a drawer, a disclosure or a single layout that works at all widths.

Breakpoints come from `media.css`: `--bp-xs` 480, `--bp-sm` 560, `--bp-md` 768, `--bp-lg` 1040, `--bp-xl` 1120 (all `max-width`), `--bp-2xl` 1320 (`min-width`). A module that uses one starts with `@import '@/styles/media.css';` (lightningcss resolves custom media per file; the import emits no CSS). Snap mockup widths to the nearest step and list the snaps in the PR. A module that forgets the import fails silently (the query never matches), so check the build: `rg -F "(--bp-" web/dist` must find nothing.

## Rule 4: state lives in hooks

State, derivations, effects and URL or storage sync go into a `use*` hook next to the page (or in `lib/` when shared). Hooks can be tested with `renderHook()` without a router or provider tree; pages cannot.

## Rule 5: layout-agnostic props

A prop answers "what does this show?", never "where am I rendered?". No `isInSidebar`, `leftOffset`, `stackVertically`. The parent positions the component by wrapping it (for example `SplashLayout` places the `IpcButton` or `IpcActionButton` its caller passes as `action` in its CTA slot). Two genuinely different presentations are two components with the same data contract.

One sanctioned exception (S14.1): the app shell provides `useInShell()` (`web/src/shell/shellContext.ts`) because it owns the page's `main` landmark and the brand mark. A full-bleed layout reads it to avoid a second `main` and a second brand link (`SplashLayout`); sizes still come from the parent through a custom property (`--shell-offset`), not from the context.

Page routes that render a full-screen splash say so in `staticData.splash` (`web/src/shell/splash.ts`), so the shell is left out before the route's chunk loads.

## Rule 6: CSS is co-located and uses tokens

- Each component imports only its own sibling `.module.css`. No component imports a page's module or another component's module; a style two places need becomes a shared component.
- Colours, fonts, durations, easings, radii and glows come from `tokens.css` custom properties. A raw value the mockup uses once (a scrim gradient, a shadow) may stay in the module; a value used in two modules becomes a token only if a mockup or `design/DESIGN.md` defines it.
- Keyframes live in the module that uses them. Continuous animations are opted in under `@media (prefers-reduced-motion: no-preference)`.
- One SVG source per graphic: the logo is `components/BrandLogo` (and `public/favicon.svg` mirrors it); never paste the same inline SVG twice.

## Rule 6b: images from UploadThing

An image from UploadThing (`*.ufs.sh`) is rendered with `crossorigin="anonymous"`, explicit `width` and `height`, and `loading="lazy"` when it is below the fold; `components/RemoteImage` does all three. Why, and the rule in full: `pages.md`, "Images from UploadThing (M10)".

## Rule 6c: shared dropdowns

A filter with many values (the archetypes) uses `components/MultiSelectDropdown`, not a row of chips and not a page-local panel (UI-DECISIONS.md). A panel that must escape a card's `overflow: hidden` goes in the top layer (`popover="manual"`) or `position: fixed`, never `position: absolute` inside the card. One placement rule on both paths (`placePanel`; anchor positioning, where supported, only tethers the panel to the button): the usable area is the viewport less 16px on every side and less the fixed bar (`--shell-offset`) at the top; the panel opens below when it fits, otherwise on the side with more room, its height is at most the CSS cap and at most the room on that side, and it scrolls inside itself, so every option is reachable on a short phone in landscape. A press anywhere on an option row toggles it and keeps the panel open (the rows are labels; the panel is focusable from script, `tabIndex={-1}`, so a press on text lands focus inside). Why and how: `pages.md`, "Costs (S14.2)", S14.2b.

## Rule 6d: shared page pieces (S14.3a)

- A page's intro band is `components/PageIntro` (title, collapsed title, deck; the shared `hsr_intro_hidden` key).
- A filter row's search with its red "Clear N" is `components/FilterSearch`; the caller sizes the box in its row through `className`.
- Roster value lists, address readers, labels, cost format and the character filters live in `lib/rosterSearch.ts` and `lib/rosterModel.ts`; a custom cost set's subscription is `stdb/useCustomCostSet.ts`; the status text hook is `lib/useAnnouncement.ts`. Pages import these, never each other.
- Do not nest a size container (`container-type: inline-size`) around another one that is a flex child: in Edge the inner flex child collapsed to 0px after a window resize (the pool's container around the search box, S14.3a). Put the outer container on the element that needs it only.

## Rule 6e: charts are markup (S14.3b)

A chart is plain markup and CSS, never a chart library or a canvas (A190 item 11). A stacked column chart uses `components/StackedBarChart`: the caller passes the columns (name, segments, total label, the accessible sentence, tooltip rows), the series (label and tone 1 to 4) and the axis title, and sets `--chart-tone-1..4` (and `--chart-plot-h` if 220px does not suit) on an ancestor. The scale (`chartScale.ts`) picks round steps for at most four grid lines. Each column is a focusable button whose accessible name carries every value, so the tooltip, legend and labels stay hidden from assistive technology; forced colours and reduced motion are handled inside. Keep the page's mapping from its data to columns a pure function with its own tests (the team builder's is `pages/teambuilder/costChartModel.ts`). The profile and stats pages are expected to reuse it; a line or scatter chart would be a new component on the same rules.

## Patterns

### Scroll-linked collapse

**What it is for:** a sticky label column or panel at the start edge of a sideways scroller that gives its room back as the viewer scrolls into the content: its visible width shrinks one pixel per pixel of scroll down to a collapsed width (an icon, a portrait), and the label on it fades under the moving edge. Reference implementation: the costs page's phone name column (`pages/costs/CostTable.tsx` and `CostTable.module.css`; `pages.md`, "Costs (S14.2)", S14.2b).

**Rules that make it feel right:**

- The width is tied one to one to the scroll, `clamp(collapsed, start - scrollLeft, start)`, with no transition on the width itself: it can neither lag nor overshoot, and the next column stays glued to the edge until the collapse.
- The layout width never changes: the item keeps its full width and paints its surface with a `::before` of `--collapse-w`, with its content clipped at the same edge (`clip-path`). Nothing in the scroller moves or lurches; the transparent rest of the item lets presses through (`pointer-events`).
- Fades are tied to the same scroll progress (`--collapse-fade`, over the first 120px) and finish before the collapsed width is reached. Content that belongs to the collapsed state (a short value standing in for a column that scrolled away) appears over 30px of scroll (`--collapse-reveal`) from `--collapse-reveal-at`, which the scroller declares as the scroll at which the real value has gone under the surface (the value never shows twice); without it the reveal follows the fade (120px). Past the collapse a soft edge grows in (`--collapse-edge`, up to 24px), so what slides under the surface fades instead of showing a cut sliver.
- Content never wraps while collapsing (one line, ellipsis at the start width, the full text kept for assistive technology and in a `title`).
- Reduced motion keeps the width link (it is the scroll itself, not an animation) and turns the fades into steps.
- Keyboard focus inside a collapsed item reopens that item to full width (`reopenOnFocus`); pointer focus does not. Keyboard focus elsewhere in the scroller must not land under the surface: give the scroller `scroll-padding-inline-start` of the collapsed width plus the soft edge while the collapse is on.
- Content that spans the scroller (an empty or error state in a full-width cell) stays in the visible box: sticky at the start edge with the scroller's width (`100cqi`, the scroller an inline-size container while it holds one).
- Hidden content stays in the accessibility tree (opacity and clipping only); a header cell keeps its header semantics; a copy drawn for the eye has empty alternative text.
- Phones only (the narrow step, 560px, and below) and only while the scroller can scroll sideways, unless a page argues otherwise.

**How to use it:** call `useScrollCollapse(scrollerRef, query)` from `lib/scrollCollapse.ts` and put its result on the scroller as `data-scroll-collapse`; spread `reopenOnFocus` on the scroller; give every collapsing element the `collapseItem` class; declare `--collapse-start` and `--collapse-closed` (lengths, and `--collapse-reveal-at` when a revealed copy stands in for a real value) on the scroller under the same query; the scroller element must stay the same for the hook's lifetime (remount its owner with a `key` to change it); `measure` may be an inline function (the latest is read, nothing re-subscribes); in the page's CSS, under `[data-scroll-collapse]`, make the items sticky and read `--collapse-w`, `--collapse-fade`, `--collapse-reveal`, `--collapse-edge`. The formulas live in `styles/scrollCollapse.module.css` (timeline path) and `collapseValues()` (script path); 120, 30 and 24 appear in both and change together.

**Browser support and fallback:** a browser with scroll-driven animations (`animation-timeline: scroll()`) takes the timeline path: each item runs a scroll-driven animation that writes `--sl` and the CSS computes the values, in step with scrolling and with no script per frame (Edge measured exact). The rest take the script path: a passive `scroll` listener writes the values on the scroller; it can trail a compositor-driven smooth scroll by up to one frame (in Edge with the path forced, one frame was up to 81px during a fast programmatic smooth scroll; a finger scroll and the wheel measured exact). Safari and Firefox were not run. The path is picked by feature detection (`CSS.supports`), never by the browser's name. jsdom tests drive the script path (stub `CSS.supports`, inject a measure, mock `matchMedia`).

### Information popover (S14.3i)

**What it is for:** a short explanation or status that most people do not need every time, behind an explicit icon, on every page: the mockups' `.infoDot` and `.infoPopover`. Reference: `components/InfoPopover` (the team builder's save spot and Auction meters; `pages.md`, "Team builder: S14.3i").

**Rules:**

- **One information symbol:** the circled exclamation mark (`components/ExclamationIcon`, A210 item 7), the default trigger. A caller may draw its own trigger (the save spot's ring, check and floppy) but keeps the button.
- **The panel** (`form="panel"`, the default): an optional `heading`, the text (`children`; a string becomes one paragraph), an optional `list`, an optional `foot` line; the mockup's surface, border, 12px radius, shadow, padding and type sizes. For anything longer than a phrase.
- **The pill** (`form="pill"`): one short line in a capsule. For a status (saved, saving, a problem's reason). Keep it under about 45 characters; the full sentence belongs in the page's hidden text or a notice.
- **Tones** (`tone`, the stable `data-tone` on trigger and panel): `quiet` for information (muted, brightening to iris on hover, focus and while open); `warning` for a problem (warning colour; the pill gets a warning edge and tint). A caller tones the trigger with `--info-rest`, `--info-active` and `--info-size` on its own class.
- **Opening:** hover after 200ms, closing 250ms after the pointer leaves the trigger and panel (crossing the gap keeps it); keyboard focus after the same 200ms (tabbing past opens nothing); a click or tap toggles (it pins a hover- or focus-opened panel, closes a pinned one); Escape closes (focus inside goes back to the trigger); a press outside, focus moving to another element, or opening another one closes it. Touch never opens by hover.
- **Timed open** (`flash`): a counter the caller bumps per new occurrence; each new value shows the panel by itself for 5s without taking focus, paused while hovered or focused, then it closes; 0 ends one still showing (the problem cleared). Never tied to a re-render.
- **Semantics** (web-guidance interest-triggered-tooltips.md, "Toggletips"): the trigger is a `button` named by the caller ("About the character budget", "Save status"), with `aria-expanded`; the panel follows it in the DOM, `role="tooltip"`, no `aria-describedby`, no live region, its content rendered only while it shows. A caller that must be heard on a change announces it itself (as the save spot does). Content is never interactive unless `interactive` is set: then the panel is a group named by its trigger, reached by Tab right after the trigger, and focus inside keeps it open.
- **Placement** (`placeInfoPopover.ts`, a pure function with its tests): below and start-aligned unless the caller passes `side="above"` or `align="end"`; it flips when the preferred side has no room, else takes the side with more room and scrolls inside; it shifts to stay 8px inside the viewport; it never covers its trigger; `gap` sets the space from the trigger (the save spot uses 16 to clear the name box).
- **Top layer:** `popover="manual"`, shown and hidden from script (no card's overflow clips it; it takes no room). Not `auto`, which would close an open menu on hover, and whose light dismiss could not be animated in Firefox.
- **Modal dialogs** (S14.3k): a modal `<dialog>` is in the top layer too, and the later of the two is drawn on top, so z-index cannot keep a panel under a dialog. While a modal dialog is open that does not hold the trigger, the panel stays closed: one already open closes when the modal opens, and a timed open is held back, then shown by its normal rule once no such modal is open (if its occurrence still stands; one that went back to 0 meanwhile stays closed). A popover inside the open modal works as usual. The signal is the platform's: the open modals are `dialog:modal`, re-read by one shared `MutationObserver` (a dialog's `open` attribute, dialogs added or removed) while any popover is mounted. Where `showModal` is missing (jsdom, older engines) pages open a modal by the `open` attribute, so there `dialog[open]` counts as modal; that choice is read once when the module loads, before any test stand-in.
- **Motion:** 160ms fade and 4px slide from the trigger's side, in by `@starting-style`, out by `data-leaving` (the script hides the panel after the fade, so the exit animates in Firefox too); none under reduced motion.

**Browser support and fallback:** the Popover API (Chromium, Firefox) or, where it is missing (jsdom, older engines), a fixed box toggled by `hidden`. No `interestfor` (Chromium only, needs a polyfill) and no CSS anchor positioning: the hover intent and the placement are the script's, the same in every engine. Safari not checked (A164).

### Modal dialog (S14.4b)

**What it is for:** every modal dialog in the app: the team builder's delete confirmation, held choice and notice (S14.3j, moved onto it), the sign-in dialog, and next the create-lobby form, its Advanced Settings over it, and every later one. Reference: `components/Dialog` (`Dialog.tsx`, `Dialog.module.css`, `dialogQueue.ts`, tests in `Dialog.test.tsx`). Guides: web-guidance `ui-components/dialog.md`, `ui-behaviors/platform-controls-dismiss-dialog.md`, `ui-behaviors/light-dismiss-a-dialog.md`, `ui-behaviors/prevent-page-scroll-under-modal-dialog.md`, `ui-behaviors/animate-to-from-top-layer.md`.

**API in short:**

```tsx
<Dialog
    open={shown}                       // the page owns it; set it false in onClose
    onClose={(value) => …}             // a close the person made: the submit button's value, '' for Escape,
                                       // the back gesture, the close button, the backdrop; never for a close by the page
    title="Delete Hyper?"              // the h2 that names the dialog
    description="It is removed…"       // optional line under it (aria-describedby); or describedBy="<id in the body>"
    actions={<button type="submit" value="delete">Delete</button>}   // the footer
    size="small"                       // 'small' (--dialog-small, 26rem, default), 'medium' (--dialog-medium, 32rem),
                                       // or 'sheet' (medium above 560px, a full-screen sheet at 560px and below)
    initialFocus={cancelRef}           // default: the first control, the close button last
    focusKey={contentId}               // a new value while open places the focus again (new content)
    dismissible={!busy}                // false while a submit is in flight: Escape, back, backdrop, close button do nothing;
                                       // without onSubmit a submit button and Enter in a field do not close it either
    canClose={() => !dirty || ask()}   // optional veto on a dismissal by the person (Escape, back, backdrop, close button);
                                       // false keeps it open (the page may open a confirmation); never asked for a
                                       // submit button's value or a close by the page
    closeOnBackdrop                    // default off: a press on the backdrop does nothing
    closeLabel="Close sign-in"         // shows the close button in the corner, with this name
    returnFocus={trigger}              // default: the browser's (the element focused before opening)
    fallbackFocus={chipRef}            // focus would fall to body (the element to return to is gone): default <main>
    onSubmit={(e) => …}                // a form of the page's own (fields in the body): the dialog stays open
    error={formError ?? null}          // a form-level error above the actions, announced politely (role="status");
                                       // pass null while there is none so the region exists before its text
    className={styles.mine}            // sets the custom properties below
    data-held-dialog=""                // data-* go on the <dialog>
>
    {body}                             // scrolls inside the dialog on a short screen
</Dialog>
```

**Rules:**

- **Native modal:** `<dialog>` opened with `showModal()`; no `role="dialog"`, `aria-modal`, focus trap or `inert` (the platform does them). The page behind is inert; scroll does not chain to it (`overscroll-behavior: contain` on the dialog and its backdrop; never `overflow: hidden` on the page).
- **Content only while open:** the `dialog` element stays mounted (rendered into `document.body` through a portal); title, body and footer exist only while `open`. So a closed dialog holds nothing to find or focus, and a page can keep a reference to the element.
- **Closing:** a submit button in the footer or body closes with its `value` (the dialog's own `method="dialog"` form, done by hand so every engine gives the value); a `type="button"` does what its handler says. The return value is reset after each close (Escape sets none). A close by the page (`open` turned false) calls no `onClose`, also when the page closes it twice before the browser's `close` events arrive (they are counted). `closedby` is `closerequest`, `any` with `closeOnBackdrop`, `none` while not dismissible, and the `cancel` event is prevented then too (and when `canClose` says no). Chromium lets a page refuse one Escape per user activation; a second Escape in a row closes anyway, so a veto that opens a confirmation should keep the input somewhere the confirmation can restore.
- **In flight:** a button that cannot act while a call runs is `aria-disabled="true"` with a guard in its handler, not `disabled`: a disabled button that has focus drops it to `body` inside the modal. The close button follows this (`aria-disabled` while not dismissible).
- **Focus after a close:** `returnFocus` after a close by the person; if that element is gone (or after a close by the page, or when the page stops rendering the dialog while it is open) and focus would fall to `body`, `fallbackFocus`, else the page's `main` (`tabindex="-1"`).
- **Form errors:** `error` renders a polite live region between the body and the footer, so a form-level error does not scroll away with the body; field errors stay next to their fields.
- **Focus rings in the body:** the body is a scroll box and clips what is drawn outside it; it keeps 4px of room (`--dialog-ring-room`, padding with the same negative margin, so nothing moves), enough for an outline with a 2px offset or the slanted ring.
- **Scroll cue (S14.4c-fix):** when the body scrolls, a shadow with a hairline shows at the edge it can scroll past, as if the content were tucked under the title or the footer (web-guidance `scrollability-affordance-hints.md`, shadows). The body's own `::before` and `::after`, sticky at its edges, take no room (their negative margins cancel their height and the gap). Chromium shows them by scroll-state container queries, Firefox by a scroll-driven animation; an engine with neither shows none and keeps the scrollbar. Every dialog has it; nothing to set.
- **Sheet (`size="sheet"`, S14.4c-fix, user ruling B):** above 560px a medium card (a page's `--dialog-width` still applies; the create dialog keeps its 30rem). At 560px and below (`--bp-sm`, the step where forms go to one column) the dialog fills the screen: full width, `100dvh` tall, no border or corner radius, padding that clears the safe areas (`env(safe-area-inset-*)`, which needs `viewport-fit=cover` in the page's viewport meta to be other than 0; not set today), the title at the top, the body growing and scrolling with the scroll cue, the error and the actions pinned at the bottom. For a form that needs the whole phone screen (the create-lobby dialog). A dialog stacked over a sheet keeps its own size (the create dialog's discard and give-up questions stay small cards). The sign-in dialog and the team builder's dialogs keep their sizes.
- **One at a time:** `dialogInTurn(order, wanted)` picks the first wanted dialog in a fixed order; the others wait closed and open by themselves when their turn comes (the team builder: delete, then the held choice, then the notice).
- **Over another dialog:** open the second while the first stays open (render it anywhere, even inside the first's body: the portal keeps it out of the first's form). It stacks on top, Escape closes it first, and focus goes back to the control in the first that opened it (the browser's; `returnFocus` makes it explicit). A nested dialog's `close`, `cancel` and `submit` never reach the outer one's handlers, and a dialog's submit stops at the dialog: it never reaches an ancestor form's `onSubmit` (React events bubble through the React tree, not the DOM, so the portal alone did not stop it). Each open dialog carries its place in the stack (`data-dialog-level`, 1 for the first).
- **Looks** (the team builder's S14.3j frame): graphite panel, strong border, `--radius-modal`, dark backdrop; 22px padding; a 17px title. A page tunes it with custom properties on its own class (the base rule has no specificity, so the page's class wins in any load order): `--dialog-width`, `--dialog-pad`, `--dialog-gap`, `--dialog-bg`, `--dialog-title-size`, `--dialog-title-weight`, `--dialog-title-family`, `--dialog-title-line`, `--dialog-title-align`, `--dialog-title-close-room`, `--dialog-title-start-room` (set it to the close room to keep a centred title centred), `--dialog-text-size`, `--dialog-text-color`. The panel is at most the viewport's height less 32px; the body scrolls, the title and footer stay. The portal changes inheritance: content inherits from `body`, not from the page's wrappers, so a custom property the content needs goes on `className`.
- **Motion:** a 200ms fade and 8px rise on open by `@starting-style`, none under reduced motion; no exit animation (the content leaves with the close). **Forced colours:** the border takes `CanvasText`.
- **InfoPopover** inside a dialog works as usual, in a second dialog stacked over a first too (only dialogs above the trigger's own hold it back, by `data-dialog-level`); one outside stays closed while a modal is open (its "Modal dialogs" rule). The Escape that closes an open popover is cancelled, so it does not also close the dialog it sits in (a cancelled Escape keydown is not a close request in Chromium and Firefox).
- **Several pages' dialogs:** `dialogInTurn` orders one page's dialogs only. A dialog that opens by itself (a held choice) could stack over the shell's sign-in dialog; not reachable today (holds need an account, the sign-in dialog is for visitors and guests), but a later page with a self-opening dialog for visitors must check the sign-in dialog's state (`useSignInDialogState`).
- **Slanted buttons** inside a dialog take the shared slanted focus ring (`web/src/styles/slantedFocus.module.css`: the fill as a clipped child layer, the ring as two clipped layers behind it, in the button's own shape; forced colours get a whole border and the system outline). Used by the landing page's "Play Now" and the sign-in dialog's buttons.

**Browser support and fallback:** `showModal`, `requestClose` (the close button; falls back to `close('')`) and `closedby` (Chromium 134, Firefox 141; without it Escape and the back gesture still close, the backdrop does not) in current Chromium and Firefox. Where `showModal` or `close` is missing (jsdom, older engines) the dialog opens by its `open` attribute and closes by removing it and sending `close`. Safari not checked (A164): `closedby` is missing there, so `closeOnBackdrop` does nothing and `dismissible={false}` relies on the `cancel` handler alone.

### Lobby settings form (S14.4c)

**What it is for:** every place that edits a lobby's settings: the landing page's create dialog now, the lobbies page's create dialog and the lobby room's settings later (the same fields in `lobbies.html` and `lobbyroom.html`). Reference: `components/LobbySettingsForm` (the main fields), its model `shared/lobby-rules/lobbySettings.ts`, the host `pages/create-lobby/CreateLobbyDialog.tsx` ([pages.md](pages.md) "Create lobby (S14.4c)").

**Rules:**

- **The model is pure TypeScript in `shared/lobby-rules/lobbySettings.ts`:** the value type `LobbySettings` (every `create_lobby` setting, the handicaps in hundredths as the module stores them), the defaults (A221 R8), the presets (`BUILT_IN_PRESETS`, `presetFromModule`, `lobbyPresetChoices`, `applyLobbyPreset`: a preset copies everything but the name and the password), `settleLobbySettings` (a guest stays Casual with Closed No Rating; a custom cost set fixes the game mode), `validateLobbySettings` (one sentence per field, to the module's limits), `toCreateLobbyArgs`, `lobbyPresetMatches` (whether the form still holds a preset), the one-lobby rule (`lobbyHoldOf`, `heldLobbyOf`, `awayLobbyOf`, `awayPromptCode`, `LOBBY_LIVE_STAGES`, `lobbyLabel`), and the number field drafts for S14.4d (`LobbyNumberDrafts`, `numberFromDraft`, `numberDraftText`: a field keeps its typed text while the value holds NaN, which validation refuses and `lobbySettingsChanged` does not count as a change). It is imported as `@shared/lobby-rules/lobbySettings`, not through the folder's barrel, so the module's bundle does not carry it. Every mirrored limit and sentence is pinned to the module by `lobbySettings.test.ts`: the name, password and number bounds (the confirm window included, through `resolveConfirmWindowSeconds`) by calling the module's own checks at each bound; the live stages by comparing with the module's exported `LIVE_STAGES`; the rest (forfeit and spectator ranges, the Deferred and NoAction rules, the guest rules, the refusal sentences, the two decisions of `membershipHold`) by the module's source text. A module change that moves a bound fails that test, not a user. Not mirrored, so shown as the module says them: whether a cost set covers the game mode and draft mode, the guest lobby switch, the creation limit. An Auction lobby needs a character budget and a minimum bid raise above 0 (user ruling, S14.4c-fix; pinned by calling the module's `ensureAuctionAmounts` with `ensureLobbyConfigInRange` over a grid of values for both draft modes; the form has its own sentences, the module names the argument).
- **The form is controlled and holds no state the host needs:** `value`, `onChange` (always settled), `rules` (`isGuest`, the published cost sets), `presets` with `presetKey` and `onPresetChange` (the form applies the preset), `errors` (all of them; the form decides when each shows), `submitCount`, `disabled`. A host keeps the value where a dialog closing cannot lose it (the create flow keeps it above the dialog).
- **Errors (`useFieldErrors`, one hook for any field list):** a field's error shows once the field was left or changed (the password while typing: a refused character), every error after a submit; `aria-invalid="false"` until then, `true` with the error in `aria-describedby` after; an error that appears on leaving or changing a field is read once through one polite region 500ms later, and the region is cleared when that error goes (so the same error is read again next time); after a failed submit the first invalid field of the hook's list (the main dialog: `LOBBY_MAIN_FIELDS`) takes focus. A second section (S14.4d) calls the hook with its own fields; which section moves focus when the first invalid field is in the other one is open. The module's refusal sentences belong to the host's error slot, not to a field.
- **Rules shown, not hidden:** an option the person cannot pick stays visible and says why, in visible words too (Ranked for a guest: `SegmentedControl`'s `disabledReason` as its description, and a hint line under the pill for touch and sighted users); a select the module fixes stays focusable (`aria-disabled="true"`, not `disabled`), ignores every change (no picker on press, no value keys, a change snaps back), and has its reason under it and as its description (a guest's roster, the game mode of a custom cost set).
- **Presets (user ruling, S14.4c-fix):** a preset sets every field but the name and the password. The "Settings Preset" select sits right after the name and the password, above the fields it sets, so the order reads as its effect (the mockup's "Advanced Settings Preset" was at the end and set only the advanced values). A pick is announced politely ("Default Auction applied."). Once a field the preset set is edited, the select shows "Custom" (a disabled option, never a choice) and the announcement is cleared; picking a preset again re-applies it.
- **Controls:** native selects and inputs in the mockup's 44px boxes (the form's module; the pills match through `--segmented-height: 44px`), 16px text at 768px and below and on coarse pointers (iOS Safari zooms into smaller text on focus), the site's segmented pill (`SegmentedControl` with `showLabel={false}`, the label sitting above it), one `InfoPopover` panel per mockup info dot (wording in `lobbySettingsText.ts`). Two fields per row, one per row at 560px and below; fields in a row line up at the top.
- **Not a credential, not an address:** the lobby password is a text field masked by CSS (`-webkit-text-security: disc` while hidden; the eye switches the mask, the type stays `text`), never `type="password"`, so no browser offers to save, fill or suggest a password and the lobby name is not taken for a username. It and every other free-text field of the site spread `NO_AUTOFILL` (`web/src/lib/noAutofill.ts`: `autocomplete="off"`, `data-1p-ignore`, `data-lpignore="true"`, `data-bwignore`, `data-form-type="other"`), and their ids avoid "name" and "password". A copy of the masked text is possible (a text field allows it), unlike a password field.
- **Advanced Settings (S14.4d)** extends the same value: new fields in the form (or a second form over it, per the L3 ruling), no new model.

## Rule 7: tests

- **What gets a test:** every validator, guard and pure helper (a table of kept and dropped inputs, idempotence where the router re-runs it); route behaviour (redirects, not-found, no-access, search rewrites) through the real route tree; a page's landmarks and headline when it is added. Not every component: a component without logic is covered by the screenshot loop.
- **Where:** next to the code as `<name>.test.ts(x)`; route behaviour in `web/src/routes/routes.test.tsx` through `renderWithRouter` (`web/src/test/`). Test files under `routes/` are ignored by the route generator (`routeFileIgnorePattern`).
- **No network:** no connection, maincloud or fetch in a web test; a mocked `DbConnection` comes with M6.
- **No snapshot tests:** assert roles, text and attributes a user can see (`getByRole`, `toHaveTextContent`, `toHaveAttribute`); each test name says what it proves.
- Test files change only under a T-task (`CLAUDE.md` §6). Run with `npm run test:web`; `test/README.md` has the details.
