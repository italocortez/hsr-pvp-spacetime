# Component hygiene

Rules for every page and component PR in `web/`. They are narrow on purpose: a reviewer can check each one by reading the diff or running one grep. `CLAUDE.md` §4 holds the frontend rules these build on (subscriptions, breakpoints, screenshot loop).

## Layout

| Path | Holds |
|---|---|
| `web/src/routes/` | TanStack Router route files (file-based): thin, see Rule 0 |
| `web/src/routeTree.gen.ts` | generated by the router's Vite plugin on `dev` and `build`; committed, never edited by hand, excluded from Biome |
| `web/src/auth/` | the auth store, role helper, route guards and the `next` check |
| `web/src/pages/<page>/` | one folder per screen: `<Name>Page.tsx`, its `<Name>Page.module.css`, page hooks (`use*.ts`) |
| `web/src/components/<Name>/` | shared pieces used by two or more pages: `<Name>.tsx` + `<Name>.module.css` |
| `web/src/styles/` | the only global CSS: `tokens.css`, `media.css`, `base.css`, plus `fonts.css` (the `@font-face` rules) |
| `web/src/lib/` | hooks and helpers with no markup (`lib/legacy/` is reference only, not built or typechecked) |

Styling is CSS Modules plus tokens. No Tailwind, no CSS-in-JS, no inline `style` for static values (a `style` that passes a runtime value into a custom property is fine).

## Rule 0: thin route files

A file in `web/src/routes/` names the route and renders a page component from `web/src/pages/`. It may wire `validateSearch`, `beforeLoad` and the route's hooks (`Route.useSearch()`), but the validator, guard and page logic live elsewhere (`pages/<page>/`, `auth/`) as plain functions.

```tsx
// routes/standby.tsx
export const Route = createFileRoute('/standby')({
    validateSearch: parseStandbySearch,
    component: StandbyRoute,
});
function StandbyRoute() {
    const { module } = Route.useSearch();
    return <StandbyPage module={module} />;
}
```

In-app navigation uses the router's typed `Link` (`to`, `params`, `search` checked by `tsc`), never a string `href` on a plain `<a>`, so a typo or a missing param fails the typecheck and a click does not reload the page.

## Rule 1: thin page files

A page file composes; it does not implement. It reads its hooks, picks its data and renders components. Business rules, derived data and effects live in hooks or components, so the same feature can appear in a second page or a dialog without surgery.

```tsx
// pages/standby/StandbyPage.tsx
export function StandbyPage({ module }: { module?: string }) {
    const moduleName = useRequestedModule(module);
    useDocumentTitle(moduleName ? `${moduleName} — Standby — IPC Battlegrounds` : 'Standby — IPC Battlegrounds');
    return <SplashLayout /* image, labels, title, lede */>{moduleName && <p className={styles.modulePill}>…</p>}</SplashLayout>;
}
```

## Rule 2: viewport-agnostic components

No component asks for the viewport (`useIsMobile`, `matchMedia` in render). One responsive page per screen (A13): the CSS adapts through the shared breakpoints or container queries; components take size or variant props when a parent needs a different presentation.

## Rule 3: responsive CSS adjusts, it does not hide real content

Media and container queries change sizing, spacing, columns and order of reading flow that stays in the DOM. They do not drop real content (text, controls, data) on one width. Decorative content, marked `aria-hidden` (a HUD line, a coordinate), may be hidden at small widths; so may a duplicate of a name that stays available another way (the brand word, while the link keeps its `aria-label`). If a phone needs a different arrangement of the same content, use a drawer, a disclosure or a single layout that works at all widths.

Breakpoints come from `media.css`: `--bp-xs` 480, `--bp-sm` 560, `--bp-md` 768, `--bp-lg` 1040, `--bp-xl` 1120 (all `max-width`), `--bp-2xl` 1320 (`min-width`). A module that uses one starts with `@import '@/styles/media.css';` (lightningcss resolves custom media per file; the import emits no CSS). Snap mockup widths to the nearest step and list the snaps in the PR. A module that forgets the import fails silently (the query never matches), so check the build: `rg -F "(--bp-" web/dist` must find nothing.

## Rule 4: state lives in hooks

State, derivations, effects and URL or storage sync go into a `use*` hook next to the page (or in `lib/` when shared). Hooks can be tested with `renderHook()` without a router or provider tree; pages cannot.

## Rule 5: layout-agnostic props

A prop answers "what does this show?", never "where am I rendered?". No `isInSidebar`, `leftOffset`, `stackVertically`. The parent positions the component by wrapping it (for example `SplashLayout` wraps `HudChip` in its corner slot). Two genuinely different presentations are two components with the same data contract.

## Rule 6: CSS is co-located and uses tokens

- Each component imports only its own sibling `.module.css`. No component imports a page's module or another component's module; a style two places need becomes a shared component.
- Colours, fonts, durations, easings, radii and glows come from `tokens.css` custom properties. A raw value the mockup uses once (a scrim gradient, a shadow) may stay in the module; a value used in two modules becomes a token only if a mockup or `design/DESIGN.md` defines it.
- Keyframes live in the module that uses them. Continuous animations are opted in under `@media (prefers-reduced-motion: no-preference)`.
- One SVG source per graphic: the logo is `components/BrandLogo` (and `public/favicon.svg` mirrors it); never paste the same inline SVG twice.

## Greps

```sh
rg "subscribeToAllTables" web/src                       # banned (CLAUDE.md §4)
rg "from '\.\./.*\.module\.css'" web/src/components     # cross-module CSS imports
rg "tailwind|className=\"[a-z]+-[0-9]" web/src          # Tailwind leftovers
rg -c "<svg" web/src                                    # inline SVGs: each should be a component
rg "<a [^>]*href=\"/" web/src                           # in-app string hrefs: use a typed Link
```
