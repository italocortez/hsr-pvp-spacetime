# S14.3c-rev: loadout versions, a stale save refused by the database (2026-11-17)

## Goal

Give every account loadout a version number so the database, not the page, refuses a save or delete based on an older copy. Backend only, plus the regenerated bindings. Test task T-S14.3c-rev. Nothing published: the loadout tables (`2d07e39`, `f14b262`) have never been published, so their shape could still change freely.

## Decision implemented

DECISIONS.md A198 items 1 and 3: a version that rises by one on every save, sent by the view; a save states the version it is based on and is refused "changed on another device" when it is older; a loadout deleted on another device is reported as deleted, so the page can offer "Save as a new loadout" or "Discard my changes". Item 2 (splitting the page's sync code) and item 4 (the conflict choice) are the frontend's.

## What changed

- `UserLoadout` gains `rev` (u32) and `firstRev` (u32, private) after `slot`. `UserLoadoutRate` gains `revFloor` (u32) after `saveCount`. No other table changes.
- `view_my_loadouts` rows gain `rev` (after `slot`). Still no id, user id, `firstRev` or timestamps.
- `save_loadout(slot: u8, baseRev: u32, name, note, code)` replaces `isNew: bool`. `delete_loadout(slot: u8, baseRev: u32)` gains the base.
- `loadoutRules.ts`: `LOADOUT_GONE_TEXT` reworded; new `LOADOUT_CONFLICT_TEXT`, `LOADOUT_REV_MAX_TEXT`, `LOADOUT_REV_MAX`; new helpers `isBaseOfLoadout`, `ensureLoadoutBase`, `nextLoadoutRev`; `consumeLoadoutSaveAllowance(ctx, userId, newRev)` raises `revFloor` in its one write.
- Deletion cascade and test wipe: unchanged (the new columns live on rows they already remove).

## Choices and why

| Point | Choice | Why |
|---|---|---|
| Width and overflow | u32; at 4,294,967,295 a save is refused "This loadout cannot be saved again. Save it as a new loadout." | The account counter rises by at most 1 per accepted save, 6 a minute: over 1,300 years to the top. Refusing costs one comparison; it never wraps |
| Check order | caller, slot, version, content, unchanged, version top, save limit, write | The person first hears which copy is current. No loop: "Keep my changes" resends with the version the view shows, which passes the version check, so an invalid payload then gets its content text. The limit stays last, so no refusal counts |
| Unchanged save | a no-op: writes nothing, keeps the version, counts nothing (also with a full window) | No write, no echo. The page already knows the stored row equals its copy at `baseRev`, so it loses nothing by not seeing a new version. It sits after the content checks, so a stored text that is no longer valid (a character removed) is still refused |
| Delete | `delete_loadout(slot, baseRev)`: deletes only at exactly that version; same loadout at another version refused "changed"; empty slot, or a newer loadout in the slot (base below its `firstRev`, 0 included), a silent no-op | Settles "delete in A while B has unsaved edits": a delete from an old copy cannot remove newer edits, and a delete of a loadout that is already gone never removes the new one in its slot |
| Slot reuse | one growing counter per account, `UserLoadoutRate.revFloor`; a new loadout starts at `revFloor + 1` and keeps it as `firstRev`; a base below `firstRev` is a deleted loadout | No extra write (the rate row is already written by every save; deletes never touch it), no new table, nothing new on the wire beyond `rev`, nothing random. A per-loadout token would add bytes to every view row; a counter per slot needs ten values for the same guarantee. Cost: only the account's first loadout starts at 1 |
| Text convention | one exact sentence per refusal, exported from `loadoutRules.ts`, pinned by the module tests, tabled in `docs/loadout/architecture.md` | The page already matches loadout refusals by their words (`useLoadouts.ts`); no reducer uses a code prefix. A "[loadout-conflict]" prefix would be sturdier against rewording but `SenderError` text is shown to the person as is, so every display would have to strip it |
| Deleted text | "That loadout was deleted on another device." replaces "That loadout no longer exists." | A198 item 3 |
| Slot taken text | unchanged | The page reacts the same way (move to a free slot) |

## What the frontend builder must now do

- Calls: `saveLoadout({ slot, baseRev, name, note, code })` with `baseRev` 0 for a new loadout and the `rev` of the row the draft was made from for an update; `deleteLoadout({ slot, baseRev })` with the `rev` the page shows.
- View: `view_my_loadouts` rows are `{ slot, rev, name, note, code }`. Keep the `rev` of the row a draft is based on in the stored draft. Take a new loadout's `rev` from its row; do not assume 1 (only an account's first loadout is 1). After a successful update the row arrives at `baseRev + 1`; after an unchanged save no row changes and the version stays.
- Refusals (exact texts):

| Text | From | Intended reaction |
|---|---|---|
| That loadout slot is already in use. Your list was refreshed; save again. | save, base 0 | move the new loadout to the lowest free slot, save again with base 0 |
| That loadout was deleted on another device. | save, base above 0 | tell the person; "Save as a new loadout" (base 0, free slot) or "Discard my changes" |
| That loadout was changed on another device. | save | hold the draft; "Keep my changes" (resend with the `rev` the view now shows) or "Use the account copy" |
| That loadout was changed on another device. | delete | show the newer copy; ask again (delete with its `rev`) |
| This loadout cannot be saved again. Save it as a new loadout. | save | offer "Save as a new loadout"; unreachable in practice |
| Your loadout was not saved yet: too many saves in a short time. It will be saved in a moment. | save | unchanged (retry with backoff) |

- The content guesswork of S14.3c (`base` content compared with the row, `sent` contents) can go: the version decides. The client scenarios of `docs/loadout/contract.md` tagged "Phase S14.3c execution" still name `isNew` and "That loadout no longer exists." and need the frontend step's revision.
- Files that break now (web typecheck, 3 errors): `web/src/stdb/types.ts` (`LoadoutReducersLike.saveLoadout` takes `isNew`, `deleteLoadout` lacks `baseRev`; reported at `web/src/stdb/StdbProvider.tsx:57`), `web/src/pages/teambuilder/TeamBuilderLoadouts.test.tsx:127` and `TeamBuilderLoadoutsSync.test.tsx:92` (view row fixtures without `rev`). `useLoadouts.ts` sends `isNew` (line 506) and matches `GONE_TEXT = 'That loadout no longer exists.'` (line 95). The web tests still pass (they mock the connection and are not typechecked), but against the real module the page's calls would fail.

## What the publish needs

- The loadout tables, reducers and view have never been published, so this is still the additive first publish of S14.3s: `npm run stdb:publish:test` without a wipe (new tables, a new view, new reducers), then `stdb:publish:prod` after the §C.5 check. - The frontend must ship with the new bindings in the same release.
