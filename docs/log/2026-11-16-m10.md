# M10: the image cache worker (2026-11-16)

## Goal

A service worker that keeps a copy of the UploadThing images a visitor has seen, and can never affect the app's own files. Test task T-M10. Nothing deployed, no backend change. The plan's portrait warm-up was left out on purpose (A183 item 4).

## Decisions implemented

Plan section 8.3 (D-M9 option b) with the departures recorded in A183: fixed cache name, exact host list, fallback, kill path, no warm-up.

## What exists

- `web/public/sw.js` (157 lines): intercepts only GET image requests over https to an exact host list on the default port, with no user info and no Range header; the same-origin return is the first check. Cache-first; a miss is refetched in CORS mode without credentials and stored only when it is a full 200 image with a non-zero length; if the refetch fails the page's own request is used and not stored. Cache `hsr-assets-v1`, 400 entries, oldest first, one trim at a time. On activate it deletes other `hsr-assets-*` and `hsrpvp-assets-*` caches only.
- `web/src/lib/serviceWorker.ts`: registers in production builds, in a secure context, after `load`. `SERVICE_WORKER_ENABLED` false makes the page remove the worker and its caches instead.
- `web/sw-kill.js`: a worker that deletes the caches and unregisters itself; kept ready, not served.
- `web/src/dev/devServiceWorkerReset.ts`: the dev server removes our worker and caches from its origin.
- `web/src/components/RemoteImage/`: the image rule as a component; not used yet.
- Pattern gates: gate 11 (the built worker is exactly the caching shape or the kill shape, and agrees with the page-side switch), gate 9 (the content policy allows the worker's hosts), gate 3 (dev reset marker).

## Reviews

Two independent reviews (Fable 5.2), a fix pass after each.

1. No path to the app's own origin, the database host, Discord or the login routes. Fixed: the worker could break an image that would load without it (no fallback); no kill path; every UploadThing tenant was matched; nine test gaps, one of which would have missed a bug breaking the first view of every image.
2. No blocking defect; "would let it ship". Fixed: the documented switch-off turned the suite red; a half-done switch-off was caught by nothing; an unguarded `waitUntil`. The last pass was verified by the orchestrator's gate run including the cold-cache run; not reviewed a third time.

## Deviations and open points

- Open: the warm-up (A183 item 4).
- Before the first deploy to visitors (listed in `docs/frontend/hosting.md`): the fallback under the real CSP with the refetch forced to fail; a full switch-off rehearsal with both steps; Firefox and Safari. Only Edge was checked.
- Known and accepted (in the hosting doc): the cap goes by first store; a wrong 200 or a file deleted at UploadThing stays cached until evicted or the name is bumped; an old worker can re-create an emptied cache after a bump; the refetch sends no `Accept` header; limits of gate 11.
- The cold web run prints four "Failed to fetch dynamically imported module" lines: expected output of `web/src/shell/signInLoader.test.tsx`, which rejects a chunk load on purpose.
