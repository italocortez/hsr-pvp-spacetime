# S8g — Colours per bracket match; the head start stays with the winners' bracket finalist (2026-11-08)

Executed by the orchestrator session (Fable) with Opus sub-agents under the roles rule (Opus implements and writes tests, Fable reviews, the orchestrator never edits module code): implementer, independent reviewer (**Fable**) over the raw diff in parallel with the test task T-S8g (**Opus**), a fix pass (Opus) after the user's triage, and a T-S8g follow-up (Opus). Plan inputs: `DECISIONS.md` **A70** (line 729), **A71** (line 741, the user's ruling on the S8g failures), A35, A27, A67(4), A69(1), A25, A37; `docs/log/2026-11-08-s8e.md`.

## Goal

Let every bracket match of a tournament, group stage included, choose which team plays Blue, editable until the first game of the match is played, so a team can take Red (some prefer it over Blue's first pick) while the A27 head start stays with the team that earned it. User, 2026-11-08: "whoever gets to the grand final can decide if they wanna play red or blue"; "should be an option for every match in the tournament"; "the choice of color should also apply to group stage matches"; and on the failures: "the point should go to whichever got it from the winner brackets into the grand final … colors should be independant of whoever team picks blue or red, the score for team1 and team2 should not change".

## Decisions implemented

A70(1) per-match colour mapping with A35's default and the stale fallback, read by every colour ↔ team site; A70(3) `set_match_sides` for `bracket` staff on a Ready match, blocked once a game has started or while a lobby exists; A70(4) the mapping on the public row. **A71** (superseding A70(2)): the head start is never a colour: `team1Games` starts at `winnerAdvantage` whatever the colours (A27, A69(1) as written); `headStartSide` removed before it ever shipped; the reducer is `set_match_sides(bracketMatchId, blueTeamId)`; a slot change resets the colour choice and rewrites the tally. Group-stage matches accepted like any other.

## Rules as implemented

- **Mapping** (`helpers/matchSides.ts`, the one place): `sideSlot(match, side)` = the slot (1 = team1, 2 = team2) playing a colour: Blue is slot 2 only when `blueTeamId === team2Id`, otherwise slot 1 (unset or stale → A35 default). `sideTeamId`, `teamSideOf`, `matchSides` derive from it; `slotChangeReset(match)` = `{ blueTeamId: undefined, team1Games: winnerAdvantage, team2Games: 0 }`. No other code compares `team1Id` with a colour (grep gate: the two remaining mentions describe the default).
- **Seating** (`helpers/tournamentLobbySides.ts` `allowedSlotsFor`): the shared core `@shared/lobby-rules` is unchanged; its `team1*` inputs mean "the Blue side" and receive the Blue team's members and approved stand-ins, `team2*` the Red team's. Auto-seat on join, `set_team_slot` and `create_tournament_lobby` stand-ins follow the match's colours.
- **Credit and tally** (`helpers/tournamentResults.ts` `recordWinnerTeamId`, `helpers/bracketResults.ts` `matchGames`): `team1 = winnerAdvantage` (A71(1): the head start is slot 1's, the winners' bracket finalist), `team2 = 0`; each Validated record credits the slot playing its `winnerTeamSide`. Decide at ceil(bestOf / 2), rollback, resolve, override and DQ are unchanged: all go through `matchGames`.
- **DQ** (`reducers/tournamentAdmin.ts`): the force-concede names the colour the DQ'd team plays (`teamSideOf`).
- **Slot change** (`placeEntrant`, `setSlotBye` in `bracketStore.ts`; `unplaceEntrant` in `bracketResults.ts`): `slotChangeReset` is spread into the same `updateWithAudit` as the slot write, so a feeder rollback or a DQ that replaces a team voids the colour choice and leaves the stored tally equal to the derived one (A71(3)).
- **`set_match_sides`** (`reducers/bracketSides.ts`), guard order and messages: "Bracket match not found." → "Tournament not found." → "You are not authorized to set the sides of this match." (`hasTournamentPermission(…, 'bracket')`, A25) → "Tournament is over." (Completed / Cancelled) → "{positionKey} is {state}; sides are set on a Ready match." → "blueTeamId must be one of the match's two teams." → "The sides can no longer be changed: a game of this match has started." (any record Pending / Submitted / Disputed / Validated; Voided / Rejected do not block) → "Close the open lobby of this match before changing its sides." (a lobby of the match: after the record check this can only be a Waiting lobby, or one whose records are all Voided / Rejected). Then `updateWithAudit` with the caller's id when the value changes, and `writeMatchGames`. Setting the current value writes nothing. Group-stage matches accepted (`bracketSide = Group`).
- **Shuffle guard** (`reducers/lobbySettings.ts`): "Seats in a tournament lobby follow the bracket's sides (A35 / A70); shuffling is not available." Group standings (`tournamentStandings.ts`, `shared/bracket/standings.ts`) stay team-based.

## Findings and deviations

1. **Head start by colour was the wrong model** (A70(2), review #1, T-S8g): the user's intent was always "the winners' bracket finalist keeps the point; colours are free". A71 supersedes A70(2); the colour field was removed before it was ever published. Lesson: when a user frames a rule in the UI's words ("Blue vs Red"), confirm whether the rule is about the team or about the colour before encoding it.
2. **Guard order** (review #2): the brief listed the lobby check before the record check; fixed.
3. **Slot change** (A71(3)): the colour choice is voided and the tally rewritten whenever a slot changes; the read-side fallback stays as a defence.
4. **Scope additions by the implementer**: `docs/tournament/architecture.md` updated in the fix pass because it described choosing the head start (within the step); `view_my_tournament_matches` binding carries the new column because the view projects the bracket row.
5. **Clear-publish**: `blueTeamId` sits before the audit columns without a default; the next test1 publish (S11) is a clear-publish as planned.
6. **Usage numbers** are the harness task-notification figures; the agents' self-estimates ran low again.
