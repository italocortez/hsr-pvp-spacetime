# M5b: Discord login functions, local runner, sign-in flow (2026-11-14)

## Goal

The browser half of the link-code login: the two functions, a way to run them on localhost, the sign-in panel and the confirm step. Test task T-M5b. Nothing deployed.

## Decisions implemented

A46, A173 (own hooks), A174 (Vercel is prod only), A175 (local login, one Discord application, `.env.example` rework), A176 (two-step link), A177 (link token), A178. The "Requirements for M5b" list in `docs/auth/architecture.md` was the security specification.

## What exists

- `api/auth/discord/{start,callback}.ts` (thin shells) over `api/_lib/` (handlers, config, sealed state cookie with AES-256-GCM and an HKDF key, cookies, outbound calls with 5 s timeouts). `shared/auth-flow.ts` holds what the function and the page share.
- `start`: same-origin JSON POST only, exact Origin check, sealed `__Host-` HttpOnly state cookie, returns Discord's authorize URL (`prompt=consent`, scope `identify`). The link code is never in a URL.
- `callback`: fails closed before any outbound call; state compared in constant time; token exchange, `users/@me`, the handle (not the display name), a fresh 32-byte confirm token whose hash is presented with the link token through the HTTP reducer route; the token reaches the page in a 2-minute readable `__Host-` cookie; redirects are fixed paths.
- Local runner `scripts/local-auth/localAuth.ts`: mounted by a dev-only Vite plugin (loaded lazily, so a build never resolves `scripts/`) and by the preview server; test target only; loads `.env.test.local`; names missing keys without values.
- App: `useRows`, `useReducerCall`, `signIn.ts`, `signOut.ts`, the sign-in panel on `/?login=1` (splash pattern), the confirm step bound to the live pending row, lobby id rule.
- Gate 10 (secret key names and import fences), gate 3 needle for the dev-only loopback rule, `scripts/ci/import-specifiers.mjs`.
- Test publishes add `--yes=break-clients`. `.env.example` reworked (names and comments only).

## Reviews

Two independent security reviews (Fable 5.2), a fix pass after each (fresh Opus implementer for the fix passes).

1. No wrong-pairing path. Fixed: a deploy blocker (the build config reached `scripts/`, which is not uploaded); the confirm click linked whatever was pending, not the account shown; any 530 body shown as a refusal; the deployed function trusting `request.url` and accepting the test target; a third-party request could cancel a sign-in; connection loss shown as a refusal; gate 10 limits; test gaps.
2. Every fix held (59 mutations, 50 killed; the survivors became tests). Fixed: a `blob:` address form, a start timeout, control characters in refusal texts, gate 10 import forms. Accepted for now and documented (A178 item 8): the narrow same-user two-tab window. The last pass was verified by the orchestrator's gate run; not reviewed a third time.

## Deviations and open points

- Implementers: the test runner was run directly once; one browser command printed a single one-time confirm token for test1 (expired within two minutes; no configured secret was shown); a few helper scripts were written through heredocs; an editing tool wrote invisible characters as raw bytes in three files, found and rewritten as escapes.
- Test users left on test1 by the browser checks: a few guests and stub-linked accounts; the next live suite run wipes them.
- Unproven until the user's real Discord test: the real token and user exchange, the registered redirect addresses, Firefox's handling of the Strict cookie.
- Unproven until a real Vercel deploy: the handler export shape, compiling `shared/` from `api/`, Node 26, the settings (`AUTH_ORIGIN`, `STDB_TARGET=prod`), header rules on function responses, the duration limit against a 15 s worst case, a rate limit on `/api`, the maintenance answer of the HTTP call.
- Open: A177 item 5 (staff new-device approval before prod).

## Real Discord test (same day, by the user)

- Dev server, `http://localhost:5173`, test database, the user's own Discord application and account.
- First try: Discord answered "Invalid OAuth2 redirect_uri" (the return address must match the portal entry exactly; nothing was changed on the site). After that was corrected, the sign-in linked in Edge: user `nath.is.dead`, not a guest, login method discord (read back from test1).
- The account was deleted on the user's request (`npm run stdb:manage-user -- --target test delete <username>`) and the first-time sign-in repeated in Firefox: linked again. Firefox exposes the `SameSite=Strict` confirm cookie after the return from Discord.
- Still unproven: the re-point path with real Discord (a second browser signing in to an existing account; covered by module tests and the stub), Safari, everything on Vercel.
- Note for the profile page: a Discord handle can contain dots, and the hosting rewrite answers 404 for an address whose last segment has a dot. Public profile addresses must use the numeric id, or the rewrite rule must change.
