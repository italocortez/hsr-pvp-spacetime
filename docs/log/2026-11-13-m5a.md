# M5a: module side of the Discord login, link codes (2026-11-13)

## Goal

The module half of the link-code flow (A46): a guest requests a one-time code, reads it through its own view, and the auth function links a Discord user by that code. In-memory tests (T-M5a). Nothing published: test1 still runs the previous module.

## Decisions implemented

A44(3), A46, A175. Orchestrator's choices recorded in A175: the browser nonce as the source of secrecy, a refused merge throws its own text, `server_link_provider` stays, the Discord id shape rule on the by-code path, the name clean-up.

## Behaviour

- `request_link_code({ clientNonce })`: a live guest only (maintenance, no account, deleted or banned, already linked are refused with their own texts). `clientNonce` is exactly 43 base64url characters (32 bytes from the browser's CSPRNG), never stored or logged. One code per identity; a new request replaces the old. Five minutes.
- The code: SHA-256 (written in the module, checked against a reference on 1,255 inputs by the reviewer) over tag, nonce, identity, connection id, timestamp, previous code, attempt; first 24 bytes as base64url (32 characters). The host seeds `ctx.random` from the transaction timestamp (SDK 2.15.0 `makeRandom(this.timestamp)`), so the secrecy rests on the nonce.
- `view_my_link_request`: the caller's own row, `code` and `expiresAt` only; the client compares the expiry (views have no clock).
- `server_link_by_code({ linkCode, provider, providerId, providerName })`: server identities only. A Discord id must be 17 to 20 digits. Unknown, used and expired codes share one text. For a live code, an account that changed since the request, or a merge refusal (ban, input, the live-game rule A113(4)), throws its own text and the code stays live until it expires or is replaced. Success deletes the row and applies the merge in one transaction.
- The merge lives in one shared helper (`planProviderLink` checks, `applyProviderLink` writes) used by both link reducers. Behaviour of `server_link_provider` is unchanged except: the empty-identity check now runs after the provider and ban checks, and provider names lose control characters and are cut on a code point boundary.
- Clean-up: up to 64 rows examined per `request_link_code`; the weekly identity GC examines up to 10,000; user deletion and the test-data wipe remove rows.

## Deviations and open points

- The implementer ran `npx --version` once and the test runner directly once, against the brief (nothing installed).
- Not proven on the real host: delete-then-insert of the same unique identity in one transaction, view re-evaluation cost, reducer argument visibility (read in the SDK source only). The publish and the M5b live check settle these.
- Open rulings (A175): the optional two-step link, sign-in during maintenance, the guest-creation switch blocking new-browser sign-ins.
- No rate limit on `request_link_code` (same as other identity reducers); the guest-creation breaker bounds new identities.
