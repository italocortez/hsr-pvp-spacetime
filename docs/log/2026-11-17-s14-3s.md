# S14.3s: team builder loadouts on the account; no light cone on an EMPTY pick (2026-11-17)

## Goal

The backend for saved team builder loadouts of verified accounts (table, two reducers, one view, lifecycle), and one draft rule: `equip_lightcone` refuses an `EMPTY` pick. Test task T-S14.3s. Nothing published: the step ends with the user-gated publish to test1.

## Decisions implemented

A190 items 1, 3, 15 (verified accounts only; 10 on the account; a loadout keeps team, modes, cost set and Auction budgets in its packed text; note 1,000; name 40). A191 item 4 (no light cone on an `EMPTY` slot). A192 item 3 (the packed text, version 1, with the per-slot bid). Specification: `tmp/teambuilder/loadout-backend.md` (local), with the step brief's rulings taking precedence.

## What exists

- `UserLoadout` (`user_loadout`, private): `id` autoInc PK, `userId`, `slot` u8, `name`, `note`, `code`, audit columns; btree `user_id` and `by_user_and_slot`.
- `save_loadout(slot, isNew, name, note, code)` and `delete_loadout(slot)` in `reducers/roster/userLoadouts.ts` (the file kept empty since S10j); rules and texts in `helpers/roster/loadoutRules.ts`. The packed text is checked with `decodeTeam` / `encodeTeam` from `@shared/teambuilder` (no change to `shared/`), with a catalog of primary-key lookups on `HsrCharacter` and `HsrLightcone`.
- `view_my_loadouts` (`views/loadoutViews.ts`): `slot` (primary key), `name`, `note`, `code`; a guest or an identity with no user gets no rows.
- `ensureVerifiedUser(ctx, message?)`: optional guest text; every existing caller passes none (texts unchanged, existing tests green).
- Lifecycle: `performUserDeletion` deletes the user's loadouts; `server_nuke_test_data` clears the table.
- `equip_lightcone` refuses `characterName === 'EMPTY'`: "A light cone cannot be equipped on an empty pick." (`EMPTY_LIGHTCONE_TEXT`).

## Part 2 findings

- `equip_lightcone` is the only writer of `EquipLightcone` steps; Classic and Auction share it (the Auction draft has no light-cone path of its own). An `EMPTY` pick (manual or timer) and an `EMPTY` sale both put `EMPTY` in `teamDraft(...).characters`, so the draft check alone accepted them. The new check runs after the caller, window, throttle and step-room checks, on the open and the Admin path.
- `set_eidolon` already refuses `EMPTY`. `arrange_lineup` takes no light cone. `SKIP` is never in a team's draft.
- `unequip_lightcone` is left open on `EMPTY`: a cone equipped before the rule can be removed and refunded. Existing data: none on prod; on test1 any such step stays in its game's log and counts in that game's roster cost until unequipped or the game ends. No migration.

## Deviations and open points

- A blank name is refused ("Loadout name cannot be empty.") instead of the design's "Untitled", following the step brief ("name trimmed, required"). The page supplies a default name.
- The design's separate texts for eidolon and superimposition out of range are not used: the codec reports them as an unreadable slot, so they get the general text "This team could not be read. Reload the page and try again." A character twice keeps its own text.
- The canonical-text check is defensive: the version 1 grammar has one spelling per team (no leading zeros, a zero bid not written, lower case), so every text that decodes already re-encodes to itself. The test proves the variants are refused, not which check refuses them.
- `delete_loadout` refuses a slot above 9 with the slot text (the design only named the empty-slot no-op).
- `view_my_loadouts` also reads the caller's `User` row so a guest gets no rows explicitly (one primary-key read).
- Live suite: the design's line (`user_loadout` in `PRIVATE_TABLES`) belongs to `test/live/auth-subscriptions.test.ts`, outside the brief's file list. Instead `view_my_loadouts` was added to `PER_SENDER_VIEWS` in `test/live/outsider-isolation.test.ts` (an unmapped identity receives no rows). The file's header comment still said "38 per-sender views" (now 39). Not run. Both done in the fix pass (task T-S14.3s-live, see "Review").
- The CLI printed "A new version of SpacetimeDB is available: v2.15.0 (current: v2.14.1)" during generate (its own update check) and "tsc not found in node_modules"; the build finished regardless.

## Open points (from the review's minor findings)

- A blank name is refused, so the page (S14.3c) must never auto-save an empty name: substitute a default or hold the save while the field is empty, and never show the refusal as an error.
- A name of only invisible characters (U+200B, U+2060) is accepted, as are control and bidi characters; only the owner reads names today. Suggested later: refuse `\p{Cc}` / `\p{Cf}` and treat a name with no visible character as empty.
- An unchanged save rewrites the row (new `lastModifiedDate`) and re-sends it through the view; suggested: return early when name, note and code are equal.
- Abuse estimate: one scripted verified account at the allowance cap (20 writes per 10 s, all month) costs about 8 % of the monthly budget (calls plus the echo of worst-case rows). Accepted for test; before prod, decide whether loadout saves get a slower allowance of their own (for example 6 per 10 s; a column on `UserRateState`).
- The single-column `user_id` index is redundant: `by_user_and_slot` serves a prefix scan. Dropping it later is a safe migration.
- `view_my_loadouts` serves a soft-deleted account's rows for up to 5 s, like the other own-rows views; adding `|| user.deletedAt` would cost nothing.
- Server identities (Owner, Delegates, the scheduler) can save loadouts as SYSTEM, as with the roster reducers. No impact.

## What the publish needs

- Additive: one new table, one new view, two new reducers; code changes elsewhere. Automatic migration accepts a new table: `npm run stdb:publish:test` without a wipe; later `stdb:publish:prod` (`--yes=migrate`) after the §C.5 schema-delta check.
- `--yes=break-clients` pre-answers the CLI's question when a publish would break connected clients (a schema change their bindings cannot read). Nothing here changes an existing table, view or reducer signature, so connected clients keep working with their old bindings; they simply do not know the new view and reducers until they reload the new build. The test publish passes the flag anyway.
- After the publish: `npm run stdb:describe:test` to confirm `user_loadout` is private and `view_my_loadouts` is listed.
