# S10m — forced "require verified", sign-in guard and guest clean-ups (2026-11-10)

## Goal

Implement A113: a tournament where a guest cannot play requires verified accounts by rule, and the remaining rough edges of the guest sign-in path are closed. A114 to A116 were recorded during this step and are implemented in S10n.

## Decisions implemented

- **A113(1)**: `requireVerified` is stored as true when the tournament counts towards rating, requires a roster, has a minimum MMR above 0, requires ownership, or has a roster visibility of `OpenRoster` or `ClosedWithRating`.
- **A113(2)**: an update that would turn it on while guests are enrolled is refused with their number.
- **A113(4)**: signing in to an existing account is refused while the guest is a seated player in a running game.
- **A113(5)**: calendar invites for the tournament's match events follow a moved entry.
- **A113(6)**: a guest cannot be made a tournament assistant.
- A113(3) and (7) change no code (stats of a guest's earlier games stay on the guest account; a guest session's entry goes to whichever account signs in on that browser).

Independent Fable 5.2 reviewer, read-only, ran the suites itself, verdict **COMMIT AFTER FIXES**: the code is correct against A113 and needed no change; the two gating items were this log and the contract rows, both done by the orchestrator. No path leaves a trigger on with `requireVerified` off except rows written before A113; the guard runs before any write and exactly on the path that deletes the guest; no player can be stranded by it (concede, or leave and take another lobby with `abandonCurrentMatch`).

## Findings and hand-offs

- **Disqualified guest rows are not counted** by the A113(2) refusal (implementer's deviation from the brief, confirmed by the review): no reducer can remove such a row, so counting it would block the organizer for ever.
- **Open for the user (review F3): removing an approved guest takes a disqualification.** `reject_participant` only removes pending or waitlisted rows, so an organizer who wants to turn a gate on must disqualify approved guests; the Disqualified row is permanent and A112 moves it to the account the guest later signs in to, which can then never register in that tournament. Options: let `reject_participant` remove a guest's entry, or accept.
- **Rows written before A113** (review F4) with a trigger on, `requireVerified` off and a guest enrolled would refuse every `update_tournament`; moot with the S11 clear-publish.
- **Found while answering the user (not part of this step): the `autoRandomPick` start check** in `start_draft` requires every seated player to have a selected game account with characters, whatever `requireOwnership` says. A guest cannot have a game account, so a lobby or tournament preset with `autoRandomPick` on can never start a draft with a guest seated. Recommended fix put to the user: apply the check only when the lobby requires ownership.
- Untested parts of A113 (review F5): the Disqualified exclusion, waitlisted and awaiting-approval guests, an away seat, a second identity, a responded invite, `minimumMmr` 0.
- A disqualified guest's stale match invites move with the entry (cosmetic); a comment in `server.ts:20` cites A68(4) where A68(2) is meant.
- Deviations from a decision row: the Disqualified exclusion above.
